# SEMANTiCS SQL Database Layer

This folder contains the local analytical SQL layer used after retrieval.

The retrieval approaches should not produce final prose directly. They should first construct a typed analytical scope, then issue SQL against the same final fact table:

`fact_infectious_disease_cases_enriched`

Standard RAG and KG-RAG therefore share the same SQL database. The comparison is about whether KG-RAG builds a more complete scope before SQL, for example expanding `střevní infekční nemoci` to the complete A00-A09 block and then querying all table-present diagnoses.

## Why DuckDB

DuckDB is used because this project needs fast local analytical SQL over CSV-derived public-health facts, not an always-running transactional database server. It creates one portable database file:

`sql_database/db/semantics.duckdb`

On this EC2 instance, backend code can open that file directly. There is no service to start or keep alive.

## Folder Layout

- `scripts/create_duckdb_database.py` builds the database from the complete raw CSVs, KG JSONL files, and evaluation question JSON.
- `scripts/run_sql.py` runs any `.sql` file against the database.
- `scripts/inspect_database.py` lists tables, row counts, and the final table schema.
- `sql/00_smoke_test.sql` validates the final table.
- `sql/evaluation/*.sql` contains canonical SQL answer queries for the current evaluation questions.
- `docs/final_table_columns.json` and `docs/final_table_columns.csv` are generated by the builder.
- `COLUMN_DICTIONARY.md` is the human-readable description of the final table columns.

## Build

From the repository root:

```bash
python3 sql_database/scripts/create_duckdb_database.py --overwrite
```

The script uses the project-local `.python_packages` directory for DuckDB. It reads:

- `data/raw/infectious_diseases.csv`
- `data/raw/age_groups.csv`
- `data/raw/mkn10_cz.csv`
- `data/raw/hospitalization.csv`
- `artifacts/kg/nodes.jsonl`
- `artifacts/kg/edges.jsonl`
- `outputs/kg_rag_evaluation_queries.json`

## Run SQL

DuckDB is embedded, so “running the database” means opening the file:

`sql_database/db/semantics.duckdb`

There is no background database server to start. Any script or backend process can open this file and query it directly.

Smoke test:

```bash
python3 sql_database/scripts/run_sql.py sql_database/sql/00_smoke_test.sql
```

Run one evaluation answer query:

```bash
python3 sql_database/scripts/run_sql.py sql_database/sql/evaluation/EQ-01_intestinal_by_diagnosis.sql
```

Run any SQL file:

```bash
python3 sql_database/scripts/run_sql.py path/to/query.sql
```

Run inline SQL:

```bash
python3 sql_database/scripts/run_sql.py --sql "
SELECT
  diagnosis_code,
  diagnosis_name_cs,
  SUM(reported_case_count) AS reported_case_count
FROM fact_infectious_disease_cases_enriched
WHERE mkn_block_code = 'A00-A09'
GROUP BY diagnosis_code, diagnosis_name_cs
ORDER BY reported_case_count DESC;
"
```

Return CSV:

```bash
python3 sql_database/scripts/run_sql.py path/to/query.sql --format csv
```

Return JSON:

```bash
python3 sql_database/scripts/run_sql.py path/to/query.sql --format json
```

Limit displayed rows:

```bash
python3 sql_database/scripts/run_sql.py path/to/query.sql --max-rows 20
```

Inspect database contents:

```bash
python3 sql_database/scripts/inspect_database.py
```

Use DuckDB directly from Python:

```python
from pathlib import Path
import sys

ROOT = Path("/home/ubuntu/semantics")
sys.path.insert(0, str(ROOT / ".python_packages"))

import duckdb

db_path = ROOT / "sql_database" / "db" / "semantics.duckdb"
con = duckdb.connect(str(db_path), read_only=True)

df = con.execute("""
    SELECT report_year, SUM(reported_case_count) AS reported_case_count
    FROM fact_infectious_disease_cases_enriched
    WHERE mkn_block_code = 'A00-A09'
    GROUP BY report_year
    ORDER BY report_year
""").fetchdf()

print(df)
con.close()
```

Open a DuckDB SQL shell if the DuckDB CLI is installed:

```bash
duckdb sql_database/db/semantics.duckdb
```

Then run:

```sql
SELECT COUNT(*) FROM fact_infectious_disease_cases_enriched;
```

## Main Tables

`fact_infectious_disease_cases_enriched`

The final denormalized answer table. Both approaches should generate SQL against this table. It contains the infectious-disease fact rows enriched with official MKN-10-CZ diagnosis, derived MKN block, MKN chapter, age interval, region flags, and query-friendly normalized column names.

`infectious_diseases`

Compatibility view over the final table using the original Czech source column names: `rok`, `mesic`, `kraj_kod`, `diagnoza`, `pocet_pripadu`, and so on.

`dim_mkn10_code`, `dim_mkn10_block`, `dim_age_group`, `dim_region`

Lookup tables used to build and explain the final fact table.

`kg_node`, `kg_edge`

Flattened KG artifacts loaded into SQL for traceability and future backend experiments.

`evaluation_question` and `evaluation_scope_*`

Gold evaluation scopes loaded from the existing evaluation JSON.

## Intended Backend Contract

The backend should do this:

1. Retrieve relevant text/entity evidence.
2. Build a typed scope: diagnosis codes or MKN block, age groups, regions, years, grouping dimensions, and measure.
3. Generate SQL against `fact_infectious_disease_cases_enriched`.
4. Return the SQL result table as the primary answer.

The answer measure is `reported_case_count`. It is a reported table count and must not be described as unique patients, incidence, prevalence, or clinical evidence.

## KG-RAG Advantage Point

The SQL table is intentionally shared. KG-RAG should improve recall before SQL by producing more complete filters:

- disease-family query -> MKN block or complete diagnosis-code set
- children/seniors query -> explicit SQL predicates over `age_from_inclusive` and `age_to_inclusive`, or a complete official age-group set
- Moravia/Prague query -> explicit `region_code` filters
- absent relevant MKN code -> explicit coverage note before querying present table rows

For example, the KG-RAG route can map `střevní infekční nemoci` to `mkn_block_code = 'A00-A09'`, which returns all present A01-A09 rows in the final table.
